## القرار رقم 1: مصير المستودع (Keep vs Rewrite vs Archive)

### 1. المشكلة (Problem Statement):
المستودع عبارة عن موقع ووردبريس مسحوب (Elementor Scrape) يعاني من مشاكل في الهيكل، الأمان، تضارب الهوية، والـ SEO، ولكنه يحتوي على تصميم بصري متكامل لخدمات التسويق الرقمي. هل نحتفظ به وننظفه، أم نبنيه من الصفر بإطار عمل جديد (Next.js/Astro)، أم نؤرشفه؟

### 2. الخيارات المطروحة (Options):
* **الخيار (أ):** الإبقاء على الموقع كموقع ثابت (Static HTML/CSS/JS)، وتنظيف الهيكل بالكامل، فك الارتباط بسيرفر ووردبريس الخارجي، وتوحيد الهوية باسم محمد جمال.
* **الخيار (ب):** إعادة بناء الموقع بالكامل من الصفر باستخدام تقنية حديثة مثل Next.js أو Astro.
* **الخيار (ج):** أرشفة المستودع والاعتماد على مستودع آخر مثل `portfolio` أو `Gimy`.

### 3. مراجعة التخصصات (Discipline Review):
* **فريق الـ UX (UX-1, UX-2):** "التصميم الحالي والتقسيمات جذابة وجاهزة لعرض الخدمات. إعادة التصميم من الصفر ستستغرق وقتاً طويلاً، لذا نفضل الخيار (أ) مع توحيد أزرار الاتصال وتحسين تجربة النماذج."
* **فريق الهندسة (ENG-1, ENG-2, ENG-5):** "الخيار (أ) هو الأكثر أماناً وسرعة للنشر على GitHub Pages بدون تعقيدات بناء (Build Pipelines). نحتاج فقط فك الارتباط بـ muradmurad.com وتوفير ملفات الـ CSS محلياً وحل مشكلة الفورم."
* **فريق الأعمال والتسويق (BIZ-1, BIZ-3):** "المالك يحتاج لمعرض أعمال يعمل فوراً لدعم نشاطه التسويقي. الخيار (أ) يحقق الهدف فوراً مع ضرورة تصحيح الـ SEO وعلامات الكانونيكال لحماية سمعته المهنية."

### 4. محامي الشيطان - إدارة المخاطر (Devil's Advocate - BIZ-5):
* **الاعتراض:** "ملفات الـ CSS والـ JS الناتجة عن Elementor و Autoptimize معقدة جداً ومتداخلة. فك ارتباطها قد يؤدي لكسر بعض الحركات (Animations) أو القائمة في الموبايل لو لم نكن حذرين جداً."
* **خطة الحماية:** الاعتماد على نقطة الأمان `backup/pre-refactor-2026-09-11`، واختبار كل صفحة قبل وبعد في المقاسين (Desktop و Mobile).

### 5. القرار المعتمد (Final Decision):
* **القرار:** اعتماد **الخيار (أ)**: الإبقاء على المستودع وتأهيله بالكامل كمعرض أعمال ثابت عالي الكفاءة.
* **ليه اخترناه:** يقدم أعلى قيمة للمالك في أسرع وقت وبأقل مخاطرة ممكنة، ويحافظ على نفس الشكل الاحترافي للموقع مع تنظيفه برمجياً وأمنياً.
* **البدائل المرفوضة وليه:**
  * الخيار (ب): يتطلب وقتاً كبيراً وإتقاناً لأطر عمل برمجية والمالك مبتدئ في البرمجة ويريد شيئاً بسيطاً ومستقراً.
  * الخيار (ج): المستودعات الأخرى تعاني من نفس المشاكل وتحتاج لفحص منفصل.
* **المخاطر وطريقة التراجع (Rollback):**
  * لو حدث أي خلل في المظهر البصري، نعود فوراً لنقطة الحفظ عبر الأمر: `git checkout backup/pre-refactor-2026-09-11`.

## القرار رقم 2: حل مشكلة نموذج الاتصال (Contact Form Solution)

### 1. المشكلة:
نموذج الاتصال الحالي يرسل البيانات لـ API خارجي ووردبريس معطل، والموقع مرفوع كصفحات ثابتة على GitHub Pages (لا يوجد سيرفر خلفي لمعالجة الفورم).

### 2. الخيارات:
* **الخيار (أ):** استبدال النموذج بزر مباشر يفتح تطبيق **واتساب (WhatsApp Direct Link)** بمحتوى رسالة جاهزة، مع رابط بريد إلكتروني (`mailto:`).
* **الخيار (ب):** ربط النموذج بخدمة مجانية للنماذج الثابتة مثل **Web3Forms** أو **Formspree** (ترسل الرسائل مباشرة لإيميل المالك بدون سيرفر).
* **الخيار (ج):** الجمع بين الخيارين: نموذج متصل بـ Formspree / Web3Forms، مع توفير أزرار واتساب واضحة كبديل سريع.

### 3. القرار المعتمد:
* **القرار:** اعتماد **الخيار (ج)**: توجيه زر الإرسال الأساسي إلى خدمة نماذج آمنة للواجهات الثابتة، مع جعل التواصل عبر واتساب متاحاً بضغطة زر.
* **ليه اخترناه:** يضمن للعميل خيارين: إما إرسال رسالة فورية عبر واتساب، أو ملء استمارة الموقع لتصله على بريده الإلكتروني مباشرة.
